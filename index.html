Stop Babysitting Your Coding Agents

Decoding AI Magazine — Paul Iusztin · Sep 10

Your coding agent's harness matters more than its model — and it should run overnight on the cloud, not in your terminal.

In the sixth lesson of his open-source course "Build a Coding Agent From Scratch," Paul Iusztin takes the Decode harness built in earlier lessons and makes it headless. First, drop the TUI for a scriptable CLI (decode run "<goal>"), then ship the whole thing to Modal as serverless background jobs, then add parallel sessions. The key architectural move: the same agent loop — same model, tools, instructions — is driven by four interchangeable serving layers (TUI, CLI, remote launcher, eval harness) through one clean interface, build_agent() plus an AgentDeps bundle. That mirrors Claude Code's claude -p "<goal>" interface, and it's what lets a hobby harness grow into production infrastructure without a rewrite.

Three triggers feed the same loop: decode remote run/attempts fired from your CLI or CI/CD, an authenticated POST webhook reachable from Slack or Discord, and a nightly cron that pulls Linear tickets, implements them overnight, and pushes review-ready branches (decode/<session-id>) for you to wake up to. The "attempts" mode runs N parallel implementations of the same feature and a judge agent forwards only the best PR for review — plus observability through Opik so you can compare costs, latency, and token usage across runs.

Why this is worth your time: LangChain's Terminal-Bench experiment moved a coding agent from ~30th place into the top 5 by changing only the harness. The engineering around the model is where the leverage is. The serverless math works for bursty agent work — roughly $3.95 per H100-hour on Modal scaling to zero, versus maintaining machines on GCP/AWS. Ramp runs roughly half of its merged PRs through this kind of routing queue at production scale. One safety note to internalize: headless mode defaults to bypass permissions with ask_user as a no-op, so always cap loops with a max-requests budget and observe rather than trust blindly.

GPT-6 Astra Is Both Incredible and Frustrating

Peter Yang — Behind the Craft · Sep 9

OpenAI's newest model builds 3D games and thinks like a blunt advisor — but hesitates to actually do the work and keeps ignoring your skills.

Three things Astra does exceptionally well. First, games and 3D: it went viral for building 3D models and playable games by driving Blender and Godot through MCPs — Yang built four tech demos (Star Fox-, Call of Duty-, StarCraft-, and Slay the Spire-style) on a $20/month ChatGPT plan, documented in a 24-minute tutorial video. Second, high-level strategy: his "brutally honest advisor" prompt test produced uncomfortably blunt, useful feedback, and an intelligence-vs-cost chart shows Astra Low scoring slightly above Sol High. Third, computer and browser use: give it a photo, ask it to open jspaint.app and draw you, and it does.

Two problems hold it back as a daily driver. It often explains how to do a task instead of doing it — OpenAI's own Astra prompting guide admits the model "can stop when the user may expect it to make reasonable assumptions and persist," and recommends a custom instruction telling it to carry things through and only ask when it truly needs input. Worse, it takes liberties with his AI skills' instructions, ignoring explicit formatting rules even after he simplified them to remove conflicts — behavior he didn't see with GPT-5.6 Sol or Claude Fable.

The teaching point for your own stack: route by job, not by model. Use Astra-class models for exploration (games, strategy, one-off computer use) and keep your execution work on the model that follows your skills reliably. Higher ceiling, higher variance — the split between a "thinking model" and a "doing model" is becoming an explicit routing decision in any serious AI platform.

X — @emollick · Sep 10

Math is the preview of other professions: proofs are the flashy slice AI wins; the sustaining work around them — mentoring juniors, quality control, community, judgment — isn't automated. Oversee the Loop, Don't Sit In It

X — @emollick · Sep 10

On long-running agent tasks you can't be in the loop in detail — but you can oversee the loop. Injecting mid-run vs. forking is the same tradeoff as management.

Mollick's Codex thread: the labs could do a much better job of making agentic work visible and manageable in the interfaces they build. The platform default that follows: read-only plus explicit write gates, with a live plan the human can interrupt — "agent proposes, human releases." The Next Security Problem Is Agent Intent

X — VC list discussion · Sep 10

A chain of individually legitimate tool calls can still violate what the user meant. Goal drift over a trajectory is the new attack surface.

On the Measure of Intelligence

François Chollet (arXiv) · Sep 10

The paper behind today's symbolic-learning debate: intelligence as skill-acquisition efficiency, not demo fluency.

Chollet's argument reframed a live list discussion: asking a coding agent to invent solutions from examples is program synthesis with a neural prior — wasteful next to discrete program search plus a symbolic checker. Pair it with the hands-on sibling, DreamCoder (arXiv:2006.08381; code at github.com/ellisk42/ec), a wake-sleep system that learns a library of verified programs. The takeaway: separate neural proposal, executable checking, and a growing library of verified primitives — and measure agents by skill-acquisition efficiency, not fluency.

OpenAI Agents SDK Docs

A tiny primitive set — agent, tool, handoff, guardrail, session, trace — and the case against the framework-of-frameworks.

Today's duplication-vs-abstraction debate landed here: duplication is cheap now, the wrong abstraction is still expensive, and every extra framework layer is something the model must learn, violate, or wrap. LangGraph: Multi-Agent Concepts

LangChain (official docs) · Sep 10

Model your agents as a state machine you own — typed state slices, handoffs as commands — not a chat log.

From the agent-dock discussion: with many concurrent agents you need to know who's active, what they last did, and who they can hand off to — otherwise runs become un-debuggable prompt soup. Each specialist a node with a typed state slice; ship an operator surface showing the active node, last tool calls, and pending human gates. Start with a supervisor plus 3 tools max; add a second agent only when tool count or context size is the failure mode.

Equipping Agents for the Real World with Agent Skills

Anthropic Engineering · Sep 10

Skills — versioned, reviewable, lazily-loaded playbook folders — are the unit of agent product.

Claude Tag's on-call behavior isn't "a smarter model"; it's skills plus CLAUDE.md plus templates loaded after the repo clone. A skill is a folder with SKILL.md (frontmatter name/description, body lazily loaded), and the same format works across Claude apps, Claude Code, and the API. Spec and examples: github.com/anthropics/skills. For Riot: incident-triage, player-safety-escalation, live-ops-change-window as skills.
