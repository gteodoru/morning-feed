The durability question moved from theory to practice this week: two teams shipped answers to what happens when an agent runs for hours, crashes, or has to wait for a human — and the deepest lesson is that the bottleneck has moved from writing code to reviewing it.

Inngest vs. LangChain: I Built the Same Long-Running Agent Twice

Decoding AI Magazine — Paul Iusztin · Nov 24

The same overnight coding agent, built on two stacks — and a clear verdict on which survives a crash, a stop, and a three-day pause.

Paul Iusztin built the same overnight coding agent — CodeClimb, an eval-driven GraphRAG code-search loop — on two stacks, to answer the fear every agent builder has: if the run crashes after six hours, do you pay twice to resume? His best night ran 26 rounds in 11.8 hours for $74.63.

On Inngest, a server holds the run state and schedules steps while your worker executes; it notices a dead worker in about two minutes and can redirect or retry, and step.waitForEvent pauses a night for up to three days without holding a worker. On LangChain, the Agent Server, Postgres checkpoints and a Redis queue all live on one node — and with durability: "sync", the most real-time option, the server batches writes every second, so any step not yet saved between batches is lost; task retries live inside the server process, so a crash wipes them, and a watchdog had to be added to clean up sandboxes the server can't recover.

Verdict, 4–2 to Inngest: durability, developer experience and cost (about $1.15 a night in sandboxes vs ~$2.17 on LangSmith) against LangChain's observability and deployment. His rule of thumb: porting an existing codebase, a cracked team, or a super-custom build — Inngest as the durable engine you plug into your own code. Starting from scratch with a small team and standard patterns — LangChain, even at the higher price. Disclosure worth noting: Inngest sponsored the piece; the author says the opinions are his own and Inngest saw it at the same time as readers.

Claude Ship automates the PR review bottleneck — and Anthropic's research says reorganization is where the value is

Anthropic — via X @ClaudeDevs / @bcherny · Nov 23

Two Anthropic releases, one argument: as coding gets cheap, review — and reorganizing the work itself — becomes the choke point.

Claude Ship (beta) takes a PR through review, fixes and an approval decision based on a policy file in your repo — "like a smarter CODEOWNERS file," in @bcherny's framing. Run /ship in the CLI or desktop app; on Team and Enterprise, admins can enable it per repo so it runs on every PR. The merge gate stays where it was (branch protection, required checks) — what moves to the model is the judgment about whether a diff is safe under the policy. @PontusLenell made the sharpest point in the replies: "the policy file quietly becomes the most read document in the company. whoever writes what counts as safe to approve ends up doing the senior review once, for every PR after it."

The same day, Anthropic's economists published "Working with AI" — 66 interviews at 58 US enterprise customers, from AI-native startups to 100-year-old firms. Value comes mostly from more output, not lower costs; of 100 pieces of AI-written software described in detail, 80% automated manual work. Very few AI-driven domestic layoffs — but two-thirds of firms reported hiring less because of AI. And the bottlenecks, as coding speeds up: "code review, sales, and strategic decision-making." Top-down automation creates insecurity and surveillance fears among the experts needed to make workflows durable; handing out tools and waiting gives uneven, single-task adoption. The highest value came with reorganizing: broader roles owning whole workflows, people moved to the bottleneck tasks, infrastructure for non-developer coding.

The same-day counterpoint, via @lennysan's Atlassian episode: teams where everyone was an "AI builder," with no PM or design roles, moved "faster than ever" for a few weeks — and a month later everyone had gone back to their old jobs. A PM: "Throughput's not our problem. Direction's our problem." As @emollick summarized the paper: "The most AI value comes from changing the organization." One tension to watch: @natolambert argues readable chain-of-thought is an inefficiency that will go away — monitoring has to move from reading reasoning to testing outputs and tool calls, "while you can still read the traces to validate them."

DeepMind's agent teams proved faster quantum algorithms — in Lean, so no trust is required

Google DeepMind — via X · Nov 23

Independent teams of Gemini 4 agents, debating every four hours and proving every idea in Lean, cut quantum-circuit costs up to 290×.

Some quantum algorithms need more resources than the first error-corrected machines will have, and you can't test big circuits on classical computers — so correctness has to be proved, not tested. DeepMind's answer: separate, independent teams of Gemini 4 agents worked on each problem, every idea proven in Lean before entering a shared notebook, and every four hours the teams met at a "virtual conference" to trade and debate ideas.

Results: an inertial-confinement-fusion calculation 11.8× cheaper, with memory down from 5,650 to 4,338 logical qubits; a light-sensitive molecule simulation 8× cheaper; Cytochrome P450 — the enzyme that breaks down most medicines — 2.5× cheaper, 481 to 333 qubits; a 2.57× speedup on one Grover implementation; and a 290× speedup for arcsin, a routine used to load numbers into quantum states. DeepMind is candid that these still need more resources than the first error-corrected machines will likely have — and it open-sourced the Lean library, problem specs and verified solutions.

@fchollet's take: "A 10x reduction in simulation cost is essentially a hardware leap achieved through software." The pattern is the same as the Riemann proof: agent search plus a proof checker means you don't need to trust the agents — the verification carries the trust.

Shirudo: OpenAI and Cisco let agents write eBPF "shields" against exploits before patches land

OpenAI / Cisco — via X @gdb · Nov 23

A Linux runtime where agents write small, signed kernel controls to block an exploit path — no reboot, no downtime — while the real patch is still being built.

Shirudo — Japanese for "shield" — is an open-source Linux runtime from OpenAI and Cisco (built on Isovalent's Tetragon eBPF platform) that lets agents write dynamic eBPF controls to shield systems from exploits, buying time to test and roll out patches without downtime. A guardian agent scans code and vendor disclosures, traces a vulnerability to the affected assets and attack paths, writes a small targeted shield, and tests that it blocks the exploit while the service still runs. Shields are cryptographically signed and TPM-verified before they load, graduate to active blocking only when the evidence says they're safe, and retire when the real patch lands. In a controlled demo, a Codex-generated shield blocked a Java4Shell exploit against a running Elasticsearch process — no restart.

The replies asked the right questions: how do you validate a generated control before enforcement, and roll it back if it blocks real traffic (@MoisesAJunior)? What stops an agent from writing a bad rule (@liupingwei)? And the real containment was never the eBPF verifier but the release process — staging, canary, rollback window (@epure_liviu). This is a direct answer to last week's lead: AI-found vulnerabilities outpacing patching. The gap between discovery and patch is now a machine-speed race, and Shirudo is the defenders' first purpose-built entry.

Agent shopping is fragile: an agent's pick flips with page order, headlines, and injected "memory"

Wharton GAIL / X — @omooretweets (a16z) · Nov 23

Across 26,000 tests, agents were consistent on a bare product page — then every added bit of context made the choice less predictable.

Two studies, one warning. Olivia Moore (a16z, with The Prompting Company) ran four consumer agents — Muse, Instinct, Grok Bot, Dots — across 1,270 prompts and 11,307 runs, compared with ChatGPT, Gemini and Perplexity. Agents have default "hero products" for generic asks but respond to use-case and persona marketing; they "ruthlessly optimize value," fully loading subscription terms, returns, warranties and shipping. The practical advice: optimize for agent crawlers — clear what/cost/why, plus an API/MCP and docs for software.

Wharton's GAIL report (Aug 27; ~26,000 tests, six models) is the counterweight, via @emollick: agents were consistent when shown only a product page — but adding a review screenshot, competing sources, their order, an injected "memory," or a different retrieval method shifted the pick. "The more context we added, the less predictable the final choice became." The camps in the replies: "it's position bias" (@gpelluet27: "preferences that flip when you reorder the list aren't preferences"); "it's continuous CRO now"; "it's prompt injection from the commerce side"; and a caveat — the Wharton set is GPT-5.5 / Opus 4.8 era, so newer models may behave differently.

Takeaway: if your agents buy or recommend, the page is the prompt — and whoever controls the page controls the pick. Black Friday this week is the live stress test.

Vercel's Audited ZDR: zero-data-retention you can actually verify

Vercel — via X · Nov 23

ZDR today runs on contracts and self-attestation. Vercel's new tier has an independent firm review the serving code, run live tests — and plant canary prompts.

"Zero data retention" today relies on contracts and self-attestation. Vercel's new Audited ZDR tier on its AI Gateway changes the mechanism: a provider is listed only after an independent security firm reviews its serving code and infrastructure config and runs live tests — marked prompts sent through the gateway, then a search of logs, traces, crash dumps, prompt caches, backups, support tools and training sets. The checks include KV cache in volatile memory only, no failover from a ZDR request to a non-ZDR endpoint, and no training on customer data.

Between audits, Vercel sends canary prompts containing unique unindexed URLs — any fetch of one means someone read the prompt. The honest limit, stated by Vercel itself: canaries can't catch prompts written to disk and never read. Launch partners are Baseten, Modal and Wafer; audit reports are due by Dec. 8.

Takeaway for an AI platform handling other people's prompts: "trust us" is no longer a retention policy. Auditable ZDR is becoming table stakes — and the canary trick is worth stealing for your own verification.
