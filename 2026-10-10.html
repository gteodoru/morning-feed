Claude Code Projects: one coordinator, many cloud threads

X — @ClaudeDevs · Oct 9

Anthropic opened Claude Code Projects to every Pro and Max user on the waitlist: a coordinator conversation that runs many cloud threads, each on its own branch, opening PRs and watching them with auto-fix.

A project is one long-running coordinator conversation plus many threads. Each thread is usually a cloud session on its own branch and repo copy: it opens PRs, runs tests, watches its PR with auto-fix, pushes fixes when CI fails, and answers review comments. The coordinator sees only what threads report back.

Every thread gets shared context: project memory (MEMORY.md and files Claude writes), project instructions (up to 16,000 characters), each repo's CLAUDE.md, a file Library, and your connectors. An Overview pane shows "Waiting on you", PRs, and Routines. Threads can also run locally via Remote Control, but only while your machine is awake.

Mind the costs and limits: by default threads use Opus at high effort, which the docs say "draws on your plan fastest." There's a hard cap of 200 new threads a day, and idle threads wake — and spend quota — when CI fails or a review arrives. It's a public beta on Pro and Max, single-user for now.

Builder takeaway: start with one repo and a measurable goal (the docs use "p95 under 200 ms"), ask Claude to propose threads before launching them, keep few in parallel, and consider lower effort. Put durable rules in project instructions and repo rules in CLAUDE.md. Related: Thariq (Anthropic) says one prompt to Opus 5.5 ported his two-week Agent SDK side project to Claude Managed Agents and made it "way more reliable."

Python 3.15: lazy imports, a real profiler, frame pointers

X — @pyblogsal; @charliermarsh · Oct 9

Python 3.15 ships lazy imports, the Tachyon 1 MHz sampling profiler in the stdlib, and frame pointers by default — with same-day uv 0.13 support, whose binary is 40% smaller since July.

Lazy imports (PEP 810): `lazy import json` binds a proxy and the module loads on first use. Enable globally with `-X lazy_imports=all`, `PYTHON_LAZY_IMPORTS`, or `sys.set_lazy_imports()`, with a filter callback to exempt modules. It's module-scope only, and import errors now appear at first use with a traceback showing both locations.

Tachyon (PEP 799) is the big one for production: a sampling profiler in the stdlib that samples at up to 1 MHz with "virtually zero overhead." It can attach to a running PID, run a script, or dump the stack of a hung process (async-aware). It measures wall, CPU, GIL, or exception time and outputs flamegraphs, Firefox Profiler format, line heatmaps, or a live TUI; cProfile moves to `profiling.tracing`.

Frame pointers are now on by default (PEP 831), so tools like perf can unwind through Python — but the docs warn that "a single native component built without frame pointers can break stack unwinding for the whole Python process." Also new: frozendict (hashable, not a dict subclass), `sentinel("MISSING")`, UTF-8 as the default encoding, `[*L for L in lists]`, a free-threaded stable ABI, and a JIT that's 7–8% faster than the interpreter on x86-64 (11–12% on AArch64 macOS). 3.14's incremental GC was reverted over memory pressure. The release has 5,643 commits from 1,012 contributors.

Same-day uv 0.13 support, and Astral's Charlie Marsh detailed how the uv binary shrank more than 40% since July (“57% on Windows”), saving about 4 PB a month of mirror bandwidth: `panic="abort"`, `codegen-units=1` (which also made builds 48–60% *faster*), PGO, less monomorphization, a custom DebugNoInline derive.

Builder takeaway: measure your CLI's startup with `PYTHON_LAZY_IMPORTS=all` before adding any lazy keywords; profile production with `python -m profiling.sampling attach <PID> --flamegraph`; make sure frame-pointer flags reach your native builds. For any Rust CLI you ship: try `panic = "abort"`, `codegen-units = 1`, fat LTO, PGO on real workloads, and measure each change with cargo-bloat. And for fun: `uvx --python 3.15 whatsnewt`, Barry Warsaw's puzzle game that teaches the release — Armin Ronacher joked this is "the first release where parts of the core team started to suffer AI psychosis."

The agentic software factory hierarchy of needs

Decoding AI Magazine — Hugo Bowne-Anderson & Eleanor Berger · Oct 9

A field manual for software agents that keep working while you're away: harness, personalisation, automation, continual learning — with specification and verification at every layer.

Hugo Bowne-Anderson (who teaches LLM systems to engineers at Netflix and Meta) and Eleanor Berger (former principal engineer at Microsoft and Google) lay out four layers, each building on the last:

1. **Harness.** The environment around the model: tools, a workspace for project files, execution and feedback. If a check fails, the harness must give the agent enough information to investigate what happened. (If you're using Codex, Claude Code, Hermes, or OpenClaw, you already have one.) 2. **Personalisation.** The context for your work: project direction, rules, reference material, skills, connections to other systems. Keep it where future workers can find it — an AGENTS.md pointing into maintained docs works. Set permissions and sandboxing: "Written instructions alone don't enforce those boundaries!" Eleanor's cautionary tale: she once told an agent to write tests, and it wrote tests for a README. 3. **Automation.** A schedule or event starts work without a fresh instruction: a morning automation checks a saved task list and picks up the next agreed task. Practical details: don't start the same task twice, leave an empty queue alone, set time and spending limits, save progress so later sessions continue. With several agents, coordinate via a shared task list; combine checks — deterministic tests for balances, agent verification for missed requirements, human judgment for whether the workflow fits how you actually work. 4. **Continual learning.** Keep records of assignments, checks, and difficulties; a review agent proposes improvements to prompts, skills, or configuration, submitted for human review with evidence from the runs. Reassess as models change — Anthropic describes removing procedures as model capabilities improved.

Running through every layer: **specification** (make the outcome, constraints, and success criteria explicit) and **verification** (check the software *and* the agents' work). This is the operating manual for your AI foundation platform: start with a familiar harness and a short brief, add automation where you keep getting pulled back in, and build the learning loop where the same failures recur.

Surge's sudo L7: agents still lack staff-engineer judgment

X — @echen · Oct 9

A new benchmark tests whether coding agents act like staff engineers on fuzzy production tasks: Opus 5.5 succeeds ~45% — and the gap is judgment, not correctness.

Surge's sudo L7 benchmark asks a different question than most evals: not "can the model write correct code," but "can it act like a staff engineer?" Sixty fuzzy tasks ("can we safely cache this?"), mostly from private production repos, graded on eight dimensions including judgment and thought partnership.

Results: Opus 5.5 and Sonnet 5.5 succeed about 45% of the time, GPT-6 Astra ~32%, GPT-6.1 Sol ~30%. But functional correctness is nearly tied (Sol 82.4, Opus 82.1) — the gap is judgment. On thought partnership, Opus scores 76.1 to Astra's 51.6. Cost per task: Opus about $10, Sol just over $1.

Takeaway: the models write correct code about equally well; what separates them is pushing back on the request. Lenny Rachitsky called it "half-way there." For your platform: evaluate agents on the fuzzy stuff — judgment, pushback, partnership — not just pass/fail, and price the judgment premium deliberately.

AI in education: tutor, not ghostwriter

WSJ — The Journal; X — @emollick · Oct 9

The Journal's new episode: Google put AI in schools and test scores plummeted. A pre-registered RCT of 211 students explains why — AI as tutor: +0.28 SD retained; AI as ghostwriter: better essays, zero lasting learning.

The Journal's new episode, "Google Put AI in Schools. Test Scores Plummeted," pairs with a pre-registered RCT from Contractor & Reyes (211 Middlebury undergraduates, GPT-4o access vs. none, 35 minutes to learn an unfamiliar topic and write an essay, then an unaided test — and another a week later).

Results: test scores rose 7.2 points (0.28 SD) right away and 3.9 points (0.21 SD) after a week — for comparison, human tutoring averages about 0.29 SD. The split is the story: students who used AI as a *tutor* kept their gains. Those who let it *write* got much better essays (+1.50 SD) — but a week later without AI, the advantage was gone (−0.14 SD). Students without AI predicted a gain about 6.5x the real one.

Takeaway, in Mollick's framing: use AI to explain, not to produce, when the goal is learning — and "100x more PowerPoint or code is not always progress."

Chollet and Kapoor on recursive self-improvement

Two compact arguments against the "intelligence explosion" narrative — useful for calibrating your platform bets. Read the 1999 malware debate as a preview of agent security: permissive systems, prompts that fail, and the fix — least-privilege sandboxes.

Séb Krier's framing: "In a decade I suspect we'll look back at how we talk about AI safety today and it will feel similar" to how we talked about malware in 1999. Schneier's Crypto-Gram: e-mail worms moved malware from floppy-disk speed to seconds; the root problem was permissive systems where any program can do anything; "Do you trust this?" prompts would fail, because worms pose as friends. "Unless security is designed into the system from the bottom up, we're constantly going to be fighting a holding action." Almost all of it came true and became routine engineering: sandboxing, signed malware, phishing. Today's agents look like 1999 Outlook: powerful automation, permissive permissions, untrusted input. The fix is least-privilege sandboxes, not users clicking "allow."
