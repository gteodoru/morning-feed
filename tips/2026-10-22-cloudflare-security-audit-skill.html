Cloudflare's Security Audit Skill: the agent auditor where the checker is never the finder

Added Oct 22 · original article

Cloudflare open-sourced the agent skill that seeded its fleet-wide vulnerability hunter: six phases, adversarial validation where the checker is never the finder — and a sobering stat that one audit run finds only about half the bugs repeated runs find.

What the post is about

Daniel San (@dani_avila7, Head of AI at hedgineer.ai) posted the recommendation on Oct 22, 2026, explicitly tying it to the week's news: with the recent critical vulnerabilities surfacing in PHP, Node.js, and other core ecosystem pieces (the php2shell flaws led today's Morning Feed), it is a good time to try Cloudflare's Security Audit Skill.

The repo (cloudflare/security-audit-skill, MIT-licensed, created June 2026, ~39K stars and ~2.4K forks) is not a scanner. It is an agent skill: markdown instruction files per attack class (memory safety, prompt injection/AI-LLM, web protocol and auth, supply chain, cloud/deployment, data isolation, client-side, and more), a JSON findings schema, and two zero-dependency Node validators. It is agent-neutral — any coding agent whose model supports tool use and parallel sub-agents — and installs with one command: npx skills add https://github.com/cloudflare/security-audit-skill --skill security-audit.

The audit runs in six phases: (1) Reconnaissance — map architecture, trust boundaries, and input surfaces into architecture.md and a coverage ledger; (2) Coverage-led hunting — isolated hunter agents work ledger units while coverage critics look for gaps; (3) Candidate validation — every candidate goes to a fresh verifier agent that tries to disprove it; (4) Structured output — findings.json with three verdicts: confirmed (complete source trace plus observed result), needs_validation (an exact unresolved fact, deliberately no severity), rejected (disproved, remembered so later runs don't relitigate); (5) Independent record verification — fresh agents re-verify the final source claims; (6) Target-neutral reporting — REPORT.md and detail files derived from the verified records.

Design principles worth stealing: adversarial validation (the agent that checks a finding is never the agent that found it); severity requires impact (likelihood × impact, not checklist deviation); defense-in-depth gaps are hardening notes, not vulnerabilities; and runs are additive — later runs use prior ledgers to target gaps. Executing target code requires an OS-enforced sandbox (no external networking, resource limits); without one, leads stay needs_validation instead of being executed. Provenance: this skill is the single-repo seed of Cloudflare's Vulnerability Discovery Harness, which grew in about six weeks into a system scanning 128 Cloudflare repos continuously (described in Cloudflare's 'Build your own vulnerability harness' blog post); the skill itself was reworked in September 2026 and has been climbing GitHub's charts since.

What people are saying

The detail Daniel San singled out is the one in the README's design principles: in Cloudflare's test runs, a single run found roughly half of the vulnerabilities that repeated runs found in total — one pass does not mean your code is secure. A reply from Elev (@Elev_30) asks the natural follow-up: what did the second run start with that the first didn't? (Answer, per the design: the first run's coverage ledger and findings.) Maria Martins reported running it overnight with Droid and being surprised at how low the usage was — though an HN commenter reported the opposite (heavy token use), so cost reports conflict.

The Hacker News thread reached ~213 points. fireup.pro's take: the interest says less about the skill than about the moment — attackers already have models that read code, find bugs, and chain them into exploits, so defenders need the same machinery. devpik carefully separates three similarly named things: Anthropic's Claude Code Security (hosted product), Anthropic's claude-code-security-review GitHub Action (diff review in CI), and this — a self-installed, whole-repo audit with a persistent ledger.

The strongest endorsement comes from dev.to's 'Who Audits the Agent?' essay, which argues security review for agents has become a product category this week (agents now author 10%+ of merged PRs at Monzo; GEICO runs an agent 'war room'): the hardest problem is not finding bugs, it is preventing the finder from also being the verifier — and Cloudflare's adversarial-verification architecture may be the most important design pattern in the repo. Zentor's FAQ adds the sober note: it does not replace human review; it narrows what a reviewer must read and shows its work.

What to take away

Directly actionable on two fronts. For the SaaS: this is installable today — point a coding agent at the codebase, run it in a sandbox, and expect the first run to be a floor, not a ceiling; budget for repeated, additive runs and watch token cost (reports conflict). For the Riot platform work, the transferable pattern is bigger than security: finder/verifier separation, coverage ledgers, and machine-readable verdicts with an explicit 'unresolved, no severity' state are a template for any high-stakes agent workflow — evals, code review, migrations. It also pairs with today's php2shell story: the same class of tooling that found critical PHP-engine flaws is now open-sourced for defense, and the asymmetry (attackers run it continuously; defenders run it once) is exactly what the 'one run finds half' stat warns about.
