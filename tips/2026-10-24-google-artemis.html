Google's ARTEMIS: give your coding agent hands on a real Android phone

Added Oct 24 · original article

Google open-sourced ARTEMIS: natural language in, real taps on a real Android phone out — via MCP straight into Antigravity, Claude Code, Codex, and Cursor. Google reports 99%+ on AndroidWorld, and the community reaction splits between genuine excitement and two honest caveats: the benchmark is Google's own run, and a September attribution dispute with Minitap's mobile-use.

What it is

ARTEMIS (github.com/google/artemis, Apache 2.0, public since August 13, 2026, ~14.5K stars and ~1,550 forks as of this week) turns natural-language instructions into reliable Android automation on a real device or emulator: it opens apps, taps, swipes, types, checks the result, and captures screenshots and Logcat along the way. The pitch is aimed squarely at the gap every AI-assisted mobile developer knows — the coding agent writes the app but cannot see whether it actually works on a phone.

It reaches your tools four ways: a web console (localhost:8000, with device wizard, live screen mirroring, prompt sandbox, and execution replays), a native MCP server for Antigravity, Claude Code, Codex, Cursor, Windsurf, VS Code and others, a CLI (uv run artemis run "..." --profile flash), and a Python SDK with typed Pydantic outputs for pytest/CI integration. Setup is one script (./start.sh) that installs ADB, scrcpy, FFmpeg and Python deps; you need a device with USB debugging or an emulator, Python 3.12+, and your own multimodal model API key.

Two execution profiles: Flash, a fast reactive observe-and-act loop at roughly 3–5 seconds per step, good for routine deterministic tasks but with no plan, no final report, and no ADB shell; and Pro, a multi-agent graph at roughly 15–40 seconds per step — a Planner keeps a living Markdown plan, the Operator executes with a pre-execution safety net (XML-first, pixel fallback) and a read-only Checker verifies checkpoints and runs a final review. Grounding combines accessibility hierarchies and OCR with visual models, so it handles custom Canvas, Compose, and Flutter interfaces rather than blind coordinate taps; a small on-device accessibility helper reads screen layout (with a UIAutomator2 fallback), and history is compressed into searchable chunks so long runs stay in context.

The headline number: Google reports 99%+ task completion on AndroidWorld, Google Research's benchmark of 100+ multi-step tasks across 20+ apps. Roadmap: an Android Studio plugin, iOS support (Android-only today), on-device lightweight vision models, and real-time duplex voice dispatch.

What people are saying

The most interesting reaction comes from someone with skin in the game: Jenil Gohel, who built OpenMob — a self-hosted MCP bridge giving agents eyes and hands on phones — wrote that he assumed nobody else was building this, then found ARTEMIS does it with built-in execution intelligence (its own reasoning loops, recovery, and context management) where OpenMob leaves recovery entirely to the calling agent. His verdict: he would switch to ARTEMIS for most things, while noting OpenMob stays lighter (one binary, no Python environment) and has iOS tooling where ARTEMIS has only a roadmap.

Reviewers converge on the same honest caveats. The 99%+ figure is Google's own run on its own benchmark, not an independent retest — and a scripted benchmark is not the same as a banking or messaging app on a personal phone, where permissions and confirmation gates around purchases, messages, and private data remain essential. The practical advice emerging is hybrid: use ARTEMIS for discovery and hard bug reproduction, then encode stable checks in deterministic test suites. Flash's missing plan and final report also matter for long workflows — those pay Pro's 15–40 seconds per step.

The provenance story is worth knowing before adopting it. On September 11, Minitap (the French startup behind the open-source mobile-use library) opened issue #40 charging that ARTEMIS derived from mobile-use without credit — device-connection code, an agent prompt, even the same example and bug — and that a force push had replaced the original authors' names in pyproject.toml. Google restored README and file-header attribution on September 12, closed the issue September 15, and on September 29 moved the derived code into a third_party/mobile_use directory with its own LICENSE and METADATA (visible in the README today). No separate Google statement; Minitap's post ends at 'we'll update when there's something substantive.'

What to take away

This is the device-in-the-loop piece the agent-coding workflow has been missing: the moment a coding agent can build an APK, install it, log in with a test account, walk a flow, and hand back screenshots of what actually broke, 'it compiles' stops being the acceptance test. For the SaaS, that is directly tryable this week for mobile QA — one script, a test device, and a prompt like the README's login-screen example. For the Riot platform work, the transferable pattern is the Pro profile's architecture: planner plus operator plus a read-only checker, with a safety net before every action and an explicit incident record until recovery succeeds — the same finder/verifier separation that made Cloudflare's audit skill interesting, applied to execution instead of review.

Two diligence notes before betting on it: treat the 99%+ as directional until an independent run exists, and note the attribution episode — not as a reason to avoid it (the credit is now restored and the license is Apache 2.0), but as a reminder to check provenance when a big-company repo absorbs community code. Watch the iOS roadmap and the Android Studio plugin; either one would make this the default mobile testing layer for agent teams.
