How to actually use decision models for evals

X — @HamelHusain · Oct 20

Never trust the 0.50 default threshold: Hamel Husain and Antaripa Saha's field guide to tuning cheap classifier judges for agent evals — the most-bookmarked technical post of the day (3.4K bookmarks).

Decision models — small, cheap classifiers like TypeSafe's Jev, Perplexity's Decider, Liquid's d1, Cloudflare's Clef, OpenAI's Decisions API — are the cheaper alternative to LLM-as-judge for pass/fail evals. The experiment: 98 production traces from an apartment-leasing agent (61 known failures), asking each model 'does this trace contain a substantive failure?' The lessons: (1) Don't trust 0.50 — if every failure scores 0.40 and every pass 0.10, the model is perfect at 0.30 and useless at 0.50. (2) Set precision/recall floors first (for alerting, Husain wants 80/80); only three models could even reach that region. (3) Tune thresholds with stratified five-fold cross-validation — and even then, no threshold met both floors in ~30% of training splits. (4) Cost vs quality: Perplexity was cheapest at 0.82 cents per 100 eval runs (F1 0.79); OpenAI Decisions (GPT-6 Luna) reached F1 0.87 at 3.72 cents — about 4.5x. (5) Check calibration if you read scores as probabilities: one group of Clef traces averaged 8% predicted failure probability while 60% actually failed. For you specifically: this is the same 'big model + cheap decider' pattern from your commissioned tip — Opus 5.5 doing the work, a cheap classifier deciding pass/fail — now with a recipe for making the decider trustworthy. The post even includes a copy-paste prompt for a coding agent to tune thresholds from saved scores without new model calls. And a warning from the replies worth heeding: a judge from the same model family as the system it grades shares its failure modes — use a different lineage.

Why does every agent session start from zero?

Decoding AI Magazine · Oct 20

Paul Iusztin's fix for amnesiac agents: build an LLM wiki from first principles so each session loads only the 1–3 pages it needs.

Iusztin hit the problem doing harness-engineering research: pointing Claude Code directly at 7 large repos produced superficial answers. The standard fix — have the agent compile notes per repo, then compare — works but is cumbersome to manage and impossible to repeat, and it doesn't mix with company docs, articles, papers, and videos. His answer: an LLM wiki, a token-efficient memory layer. Read every page once, remember where it belongs, and let each agent session load only the 1–3 pages it needs instead of re-deriving context from scratch. It's the same philosophy as the retrieval discipline behind DeepInfer's cache engineering above: the expensive thing is recomputing what you already knew. For anyone building an agent platform — Riot's foundation work, or the SaaS support-triage capstone — this is the memory architecture question done right: not 'bigger context windows,' but curated, load-on-demand knowledge.

Fix the codebase before the agent: agent-readiness is the real bottleneck

Substack — @pauliusztin · Oct 19

Tereza Tizkova (Factory): when companies adopt AI for software engineering, they 'can either succeed big or fail big' — and the difference is whether the environment around the agent is ready.

Poor documentation, flaky tests, inconsistent conventions, irreproducible dev environments, years of technical debt — humans work around all of it with accumulated tribal knowledge. Agents don't have that luxury: give them a messy codebase and they generate even messier code at ridiculous speed. Factory evaluates what Tizkova calls 'agent-readiness' of a codebase before turning agents loose on it. This is the org-change playbook in one paragraph — and it lands squarely on your SaaS team's lagging AI transition. The temptation is to compare coding agents; the leverage is in the unglamorous environment work first. A concrete sequencing for your 12-person team: measure agent-readiness (docs, tests, conventions) before scaling agent usage, not after.

The internet's plumbing had a rough day

X — @charliermarsh · Oct 20

eMudhra revoked eight CA intermediates with weak keys — found by AI-assisted tooling — while PHP pre-announced two critical RCE fixes landing today at 10:00 AM ET.

Two fires in the internet's plumbing, same day. First: a researcher — reportedly using AI-assisted tooling — found that eight eMudhra intermediate certificate authorities had private keys generated with too little randomness, meaning anyone could forge trusted HTTPS certificates. Chrome blocked them by public-key hash within two hours; Mozilla distrusted them the same day; eMudhra revoked them Oct 19. As a precaution Chrome is also removing the emSign ECC Root CA - G3 (rollout Oct 27), so legitimate sites under that root need new certificates. eMudhra says the weak keys came from an April 2025 key ceremony on certified HSMs where a wrap/unwrap step produced a second, weak set of keys — unnoticed through two audits — and that ~30,000 certificates need migration. No fraudulent certificates appeared in Certificate Transparency logs. Why Charlie Marsh (uv) cares: lots of software ships its own copy of trusted roots (certifi in Python, webpki-root-certs in Rust, uv itself), so those copies keep trusting the bad CAs until updated — uv 0.13.4 ships the fix; upgrade anything that bundles CA certificates. Second: the PHP security team pre-announced a release today at 10:00 AM ET fixing two critical remote-code-execution bugs, both CVSS v4 9.2. WatchTowr claims details leaked early and reproduced one (affecting PHP 5 through 8); Cloudflare's CTO says initial WAF rules are deployed for all customers including free, 'We are seeing early attacks emerging,' and stresses the WAF is 'a STOPGAP only.' The AI angle is the same in both stories: weak keys and old bugs that sat unnoticed are now being found much faster, partly with AI help — and patch windows are shrinking.
