The test stack that makes agent output trustworthy

X — @addyosmani · Oct 5

Now on Claude Code at Anthropic, Osmani lays out the test stack that makes agent output trustworthy — E2E as ground truth, property-based tests, differential tests, fast deterministic suites.

Addy Osmani — now on Claude Code at Anthropic — posted the test stack that makes agent output trustworthy, and it blew up (430+ bookmarks in 2 hours). His argument: agents write code fast, but the code is only as good as the agent's feedback loop. If the agent can't tell it broke something, it ships the breakage confidently. His stack: example tests say what should happen; property tests say what must never happen, with thousands of generated cases trying to break the rule; E2E flows are ground truth; old-vs-new differential testing for agent-driven refactors; fast and deterministic suites (flaky tests teach the agent to retry instead of fix).

The replies are the real discussion. @asmirkn's critique: if the agent also writes the properties, it picks ones its code already passes — Addy's answer is that he manually reviews property tests in particular. On verifying UIs: give the agent a spec of expected states per view (empty, loading, error, long content, mobile width), assert on roles and text through the accessibility tree, and add multimodal screenshot checks. And @AbdullahAymanM's pushback: Claude creates tests even in projects where that isn't the convention — overkill is a real failure mode too.

The builder takeaway, straight from the thread: humans should own the spec (properties, expected UI states, E2E flows); agents can own the implementation. Review the tests the agent writes harder than the code. Kill flakiness before you hand a loop to an agent.

Can you trust an LLM-built benchmark?

X — @_can1357; X — @mitchellh · Oct 5

Tern's author claims 1.6x Ghostty's styled throughput — and Ghostty's own author replies that LLMs 'almost always deliver results you want to see.'

Can Boluk posted a chart claiming his terminal, Tern, is 1.6x faster than Ghostty on styled/OSC throughput, with 23x lower stdio latency and 40-47% less CPU — crediting xutf, his permissive UTF-8/16/32 transcoding library with SIMD fast paths for ASCII (github.com/can1357/xutf), and aggressive glyph-atlas caching. The SIMD trick works because most terminal bytes are ASCII, so you skip per-codepoint decoding for the common case — a real bottleneck when agents stream styled output.

Then Ghostty's own author, Mitchell Hashimoto, weighed in: it's fine to use LLMs to write benchmark harnesses, but you can't trust them blindly because LLMs "almost always deliver results you want to see." His second point is the generous one: even if the numbers are 100% right, the best outcome is to understand them and improve libghostty — "no need to withhold innovation at a base layer" — which helps hundreds of downstream projects. Others pressed on reproducibility: Ghostty stable or tip? (Commit 27e8b3fa8, built with native-CPU flags, says Can.)

The builder rule from this thread: if an agent wrote your benchmark harness, publish the harness, the exact commits, and the build flags — or expect exactly this reply.
