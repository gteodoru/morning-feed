Sakana and Berkeley's MASS: self-improvement when humans can no longer score the work

X — @SakanaAILabs · Oct 11

Multi-Agent Self-Supervision uses one shared model as agent, workflow optimizer and evaluator — then distills the best team trajectories back into the weights.

The problem MASS attacks is the supervision bottleneck: as AI takes on open-ended research, human experts struggle to assess the results at all. Sakana AI and UC Berkeley's answer is homogeneous recursive self-improvement — the same Qwen3.6-27B plays agent (producing a workspace of results, plots and a report), workflow optimizer (revising how agents divide work), and evaluator (pairwise-comparing workspaces). An inner loop evolves multi-agent workflows with weights fixed; an outer loop LoRA-fine-tunes the model on the best team trajectories, with the workflow text stripped from the orchestrator's training prompt so coordination is internalized.

After two complete rounds, external judges (GPT-5.5 and Claude Opus 4.8, held out of the loop) preferred the round-2 model over the base model 69.9% of the time on held-out research tasks, up from 53.9% after round 1, and scores per output token rose 1.2–1.6× on public research benchmarks. The honest caveats: Terminal-Bench and SWE-bench Verified were flat to slightly down. Two findings matter most for builders. First, the winning workflows shift information into contracts and call order (the 'hops'), not persona text — the juice is in information flow, not role-play. Second, the bottleneck is usually the optimizer, not the evaluator.

The paper's closing warning deserves the headline treatment: in a homogeneous loop, a shared blind spot can let a flawed result be produced, accepted as an improvement, and baked into the next model — and if humans miss it too, each update reinforces it. Keep an external judge out of the loop. That is the discipline that separates an RSI recipe from a self-deception machine.

Sources: arXiv — MASS paper · X — @SakanaAILabs · GitHub — SakanaAI/mass

RSI-Anything: recursive self-improvement steered by a world model

X — @LingYang_PU · Oct 11

Where MASS distills team traces, RSI-Anything uses JEPA world-model predictions to decide which candidates deserve real evaluation — and only keeps updates that pass paired checks.

Ling Yang's PhAI Labs report (reposted by Yann LeCun) starts from a different cost problem: real feedback is expensive, and as a policy changes, an old world model goes stale. RSI-Anything, built on JEPA-Anything world models, uses model predictions to select which candidates get real evaluation and which experience is used for learning, adapts the world model only when its predictions look unreliable, and retains an update only if component checks and policy–world-model compatibility checks both pass.

The reported gains are concrete: code repair rose from 26.3% to 31.2% at comparable test usage; GUI task completion rose while average actions fell 39.4%; lab planning across five policy versions jumped from 21.8% to 46.0%; and on reaction optimization it reached a 96% mean best yield against Bayesian optimization's 82% at the same 40-experiment budget. Read alongside MASS, the pattern is the lesson: both systems earn their improvements from a selection mechanism they can audit — held-out judges in one, retention checks in the other — not from letting a model grade its own homework unchecked.

Isolate, build, prove, ship: a four-step workflow for agents that have to earn trust

Peter Yang — Behind the Craft · Oct 11

Micky Shimeles' 'software factory' is an AGENTS.md plus a handful of skills — and its third step, Prove, is the one most agent workflows skip.

In Peter Yang's 47-minute episode, full-stack engineer Micky Shimeles walks through the workflow he uses to ship real apps with agents instead of slop. Isolate: a skill gives each agent its own worktree copy of the code, so several can run in parallel. Build: a code-structure skill enforces a service-layer architecture with explicit inputs and structured returns. Prove: an evidence-driven-testing skill has the agent screen-record itself testing the app and compare before-and-after states. Ship: a 'greploop' skill runs Greptile review on the PR until it scores 5/5 with zero unresolved comments — then Micky reviews it himself. The one step he never hands to agents is the final human judgment on what ships.

Addy Osmani made the complementary point twice on Sunday. Agents write code 'much better on average at scale' because verification got cheap — tests, benchmarks, specs and real end-to-end runs are now cheap to ask for. And code review only works if 'done' is defined before review starts: give the reviewer checks, not an open-ended 'find issues,' or it becomes a slot machine that always finds something. Put together: the scarce skill in agentic engineering is no longer generating code; it is specifying, in advance and in writing, what evidence would make the code acceptable.

Harness pluralism: match the isolation primitive to the blast radius

X — @mitsuhiko · Oct 11

Armin Ronacher's hot take: sometimes a VM, sometimes a sandbox, sometimes a Durable Object, sometimes just a JS interpreter — and the feed should stop battling over the one true runtime.

It is a short post with a platform-sized implication for anyone building an agent foundation: the isolation primitive should follow the task's blast radius, not fashion. A long-running untrusted workload wants a VM; a bursty tool call may want nothing heavier than a JS interpreter. Mitchell Hashimoto's note on Rex's new Activity Mode points at the other half of the runtime problem — with many parallel agents, the bottleneck becomes the operator's attention, and an activity inbox for context-switching between agents matters as much as the sandbox underneath. Design the platform for plural harnesses and a single operator inbox, not for one runtime to rule them all.

Document Evals: work backward from the wrong answer (Isaac Flath)

Isaac Flath · Oct 11

Before you tune the prompt or swap the model, open the OCR: watermarks dropped, a digit swap worth ~$600M, and a debugging method that starts at the wrong answer and walks back.

Flath's essay is the most immediately applicable read in today's edition if you ship anything over documents. His process puts the PDF beside the extraction in an annotation app linking PDF ↔ OCR ↔ notes, then runs agent Q&A with citations. The failure catalogue is humbling: table headers detached from their children, invented checkboxes, signatures that vanish, and watermarks — SAMPLE, VOID, 'not for execution' — routinely dropped, so an agent confidently cites a draft contract or a fake patient record. One swapped digit in a Berkshire Hathaway figure (278,933 → 278,333, in millions) moves an answer by ~$600M. His debugging discipline: (1) is the wrong number a hallucination or already in context? (2) if in context, wrong page or right page with bad data? (3) if right page, is the PDF or the extraction at fault? Then write the cheap check next to the failure (do the line items sum to the total?) instead of burning another full agent loop. Takeaway: eval your extraction layer separately, or every downstream eval is measuring OCR luck.
